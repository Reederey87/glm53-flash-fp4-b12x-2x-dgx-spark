# Two-Spark native Flare trial — 2026-11-15

> Historical architecture or qualification record. Current production, unresolved gates and the research pause: [docs/63](63-production-pause-checkpoint.md). Old window controllers must be adapted before reuse.

Native Flare loaded the pinned NVIDIA GLM checkpoint on both GB10 nodes and
served the original model identifier on loopback port 8001. Six API smoke
checks passed. This is a successful deployment trial, not production adoption

## What passed, and what did not

- Both standalone SM121 PyTorch compile/capture/replay probes passed. Cold
  model preparation took about 79 minutes, including 50.5 minutes of tuning,
  30 compiled forwards, cross-host binding and 59 captured graphs/rank.
- Native startup verified 166.7 GiB of exported data and reached health in
  roughly 140 seconds. Model metadata advertises 1,048,576 context tokens;
  this is not an exercised 1M-token retrieval result.
- [API smoke](../receipts/flare-trial-20261115/native-smoke.json): 6/6 passed:
  identity/context, pinned tokenizer parity at omitted Max and low/high/max,
  tool/history roundtrip, JSON schema, observed prefix reuse and closing an SSE
  stream followed by successful generation. The cancellation case closes the
  first data event; cancellation during sustained decode remains unqualified.
- Retrieval: cached c4 **3/4 exact**, cached c8 **6/8 exact**, cold sequential
  **2/3 exact**. Four neighboring-record misses, no corruption/error verdicts.
  This does not establish perfect retrieval or clear the numerical gates.
  Cold concurrent retrieval was not run. Four slots × width four does not
  exercise the historical greater-than-16-query-row route.
- Native cache planner: **86.87 GiB loaded/GPU**, **14.40 GiB cache budget**,
  **2,232,064 KV tokens**, 173 shared snapshot slots. The logical token count
  is **5.03% below** B12X's 2,350,210. Different cache layouts make raw byte
  counts non-equivalent; long-context admission and retrieval are still needed.
- Native counters were measured as per-run deltas, including zero-draft rounds.
  No counter was substituted with a lifetime acceptance rate.

## Troubleshooting and operational improvements

Every critical change was researched through Exa, then reconciled with pinned
source and local vLLM, exllamav3 and TensorFold. Web support does not replace
hardware receipts.

1. Isolated native prerequisites under the candidate tree; no host package,
   driver or kernel upgrade. Used the same uv-managed CPython on both nodes.
2. Root-owned incumbent container caches blocked standalone Triton and the
   checkpoint loader. Candidate-specific Triton/Inductor and XDG cache paths
   removed the ownership collisions; export then completed.
3. Export left substantial file cache, with available memory high but physical
   free memory below the unchanged 90 GiB gate. After all candidate units stop,
   `flare_release_file_cache.py` flushes and advises only candidate core files
   with `POSIX_FADV_DONTNEED`. Head MemFree recovered from about 15 to 112 GiB;
   file identity/size/timestamps stayed unchanged. Logical advised byte counts
   include hard links and are not reclaimed-memory measurements. The operation
   also preceded B12X restoration, whose memory gate passed.
4. Expected shutdown exposed a race: the head's peer check saw shutdown as a
   failure (head wrapper exit 1; worker exit 0). Both native ranks stopped.
   The follow-up checks the requested-stop flag before interpreting peer status
   and timeouts. Regression tests cover both intentional SIGTERM and real peer
   failure; all 17 local tests pass. This follow-up has not yet been exercised
   with a loaded native model. Rollback now includes the proven scoped cache
   release automatically before the incumbent's unchanged memory gate.

The cache approach follows [Linux fadvise semantics](https://www.man7.org/linux/man-pages/man2/posix_fadvise.2.html)
and local loader precedents. Dirty pages require a preceding flush. The shutdown
fix retains [systemd control-group termination](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html)
and bounded child cleanup; it does not leave child processes outside unit control.

## Next independent candidates

Preserve the accepted core and production rollback. Before a new window,
pre-register its treatment, controls and gate. No automatic adoption.

- Context-parallel cache sharding is the stronger capacity option while keeping
  reserve. [Upstream issue 276](https://github.com/NVIDIA/hyperflare-inference/issues/276)
  describes cross-host rank-local compilation guards. Fixing it requires a new
  export plus numerical/collectives qualification; simply enabling it is unsafe.
- A separately controlled 4→3 GiB serving reserve experiment could recover
  capacity without re-export. Source `runtime_core/memory.rs` confirms an
  explicit reserve replaces, rather than doubles, the exported reserve.
  Integrated-memory host allowances remain separate. This is a hypothesis,
  not an implemented or approved production setting; physical headroom and
  long-context stress must pass, not just the planner's token count.
- Complete the precision/numerical gates in [the audit](10-flare-precision-audit.md),
  cold concurrent/state-reuse checks and matched full speed matrix before
  proposing production adoption.
